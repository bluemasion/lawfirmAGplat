## 1. 产品目标

根据客户提供的招标文件（.docx），自动生成**完整合规的投标文件**，并经过多模型校验确保准确性。

**核心原则**：
- 结构 100% 准确（不缺项、不乱序）
- 内容大体准确（有数据的填充真实数据，没有的标记待补充）
- 格式符合规范（字体、排版、表格）

## 2. 系统能力分层

```
┌────────────────────────────────────────────────────────┐
│              程序控制层（确定性 — 代码/算法）              │
│  文档解析 · 结构排序 · 模板匹配 · 文档组装 · 格式引擎     │
│  python-docx / 状态机 / 规则引擎                         │
├────────────────────────────────────────────────────────┤
│              大语言模型层（生成性 — LLM）                  │
│  招标理解 · 需求提取 · 内容撰写 · 语义匹配 · 交叉校验     │
│  Qwen-Max / DeepSeek / GLM-4                            │
├────────────────────────────────────────────────────────┤
│              数据层（事实性 — RAG/DB）                     │
│  律所信息 · 团队简历 · 历史标书 · 资质文件 · 业绩案例      │
│  pgvector 向量检索 / PostgreSQL 结构化 / 文件存储         │
└────────────────────────────────────────────────────────┘
```

| 角色 | 负责 | 不负责 |
|------|-----|-------|
| **程序** | 解析、结构控制、排序、模板填充、表格、文档输出、缺项检测 | 理解自然语言 |
| **LLM** | 理解招标要求、生成叙述内容、语义匹配、质量审核 | 精确数据、格式控制 |
| **RAG** | 提供真实数据（律所信息/历史方案/业绩/团队） | 生成新内容 |

## 3. 完整处理流程

```
招标文件.docx
     │
     ▼
┌─────────────────────────────────────────────┐
│ Step 1: 文档解析                             │ python-docx
│  提取: 标题树、正文段落、表格、页眉页脚       │
│  输出: 原始结构 raw_structure[]              │
└─────────────┬───────────────────────────────┘
              ▼
┌─────────────────────────────────────────────┐
│ Step 2: LLM 需求结构化提取                   │ Qwen-Max
│  输入: raw_structure                         │
│  输出: tender_requirements.json              │
│  {sections[], qualifications[],              │
│   format_rules{}, evaluation_criteria[]}     │
└─────────────┬───────────────────────────────┘
              ▼
┌─────────────────────────────────────────────┐
│ Step 3: 模板匹配                             │ 相似度检索
│  从模板库中查找最相似的历史模板               │
│  找到 → 复用结构 + 微调                      │
│  没找到 → 用 Step 2 提取的结构新建           │
└─────────────┬───────────────────────────────┘
              ▼
┌─────────────────────────────────────────────┐
│ Step 4: 数据匹配                             │ RAG + DB
│  每个章节需要什么数据?                        │
│  结构化数据 → 直接查询                       │
│  非结构化数据 → RAG 向量检索                 │
│  缺失 → 标记 [待补充]                        │
└─────────────┬───────────────────────────────┘
              ▼
┌─────────────────────────────────────────────┐
│ Step 5: 逐章节生成            （核心循环）    │
│  for section in sections:                    │
│    类型A(表格/表单) → 模板引擎填充            │
│    类型B(叙述/方案) → LLM + RAG 参考生成     │
│    类型C(资质文件) → 检查有无 → 标记状态      │
│  ※ 无依赖的章节可并行生成                    │
└─────────────┬───────────────────────────────┘
              ▼
┌─────────────────────────────────────────────┐
│ Step 6: 文档组装                             │ python-docx
│  按结构顺序拼装 → 设置格式 → 生成目录         │
│  输出: 投标文件.docx                         │
└─────────────┬───────────────────────────────┘
              ▼
┌─────────────────────────────────────────────┐
│ Step 7: 多模型交叉校验（详见第 5 节）         │
│  3 个模型分别校验 → 合并结果 → 生成报告      │
└─────────────┬───────────────────────────────┘
              ▼
┌─────────────────────────────────────────────┐
│ Step 8: 人工审阅 + 增量编辑                   │
│  律师逐章审阅 → 修改 → 锁定                  │
│  补充缺失数据 → 重新生成对应章节             │
│  手动修改不被 AI 覆盖                         │
└─────────────────────────────────────────────┘
```

## 4. 模板学习机制：技术选型分析

### 4.1 需求本质

> "每次成功解析一份新招标文件，把结构存为模板，下次遇到类似的可以直接匹配。"

这个需求的本质是：**结构化知识的积累与检索**。

### 4.2 候选方案对比

#### 方案 A：强化学习（RL）

```
状态 S = 当前招标文件特征
动作 A = 选择/生成投标结构
奖励 R = 投标成功/失败 or 人工评分
```

| 优势 | 劣势 |
|------|------|
| 理论上能自动优化 | ❌ 样本量太少（律所一年做 20-50 个标书），RL 需要上千次迭代 |
| 能发现隐含模式 | ❌ 奖励信号滞后且模糊（中标/未中标有太多非文档因素） |
| | ❌ 实现复杂度高，调参困难 |
| | ❌ 可解释性差（律师不信任黑盒） |

> **结论：RL 不适合**。数据量不够，奖励信号不明确，投入产出比太低。

#### 方案 B：LLM 结构提取 + 向量相似度匹配 ⭐ 推荐

```
新招标文件
    │
    ├── python-docx 提取原始结构
    ├── LLM 标准化为 JSON schema
    │       {type, sections[], format_rules{}}
    │
    ├── 对 JSON 做 Embedding → 存入向量库
    │
    └── 下次来新文件时：
         提取特征 → Embedding → 
         在向量库中搜索最相似的 Top-3 模板 → 
         LLM 判断哪个最匹配 → 复用 + 微调
```

| 优势 | 劣势 |
|------|------|
| ✅ 不需要大量数据，第 1 份就能存、第 2 份就能匹配 | 需要好的 Embedding 模型 |
| ✅ 可解释（能展示"匹配了哪个历史模板"） | 初期模板少，匹配精度有限 |
| ✅ LLM 做语义理解，比纯规则更灵活 | |
| ✅ 渐进式学习——用的越多越准 | |

#### 方案 C：聚类分析（无监督学习）

```
积累 50+ 份招标文件后：
    所有文件结构 → TF-IDF/Embedding → 
    K-Means 聚类 → 
    发现 "政府采购类"、"企业招标类"、"框架协议类" 等簇 → 
    每个簇提取代表性模板
```

| 优势 | 劣势 |
|------|------|
| ✅ 能发现隐含的分类模式 | ❌ 需要积累足够数据（50+） |
| ✅ 自动分组 | ❌ 聚类结果不一定有业务含义 |

> **适合 Phase 2 作为增强**，初期不用。

#### 方案 D：微调专用模型（Fine-tuning）

```
收集 100+ 份 "招标文件 → 投标结构" 的配对数据
微调一个小模型（如 Qwen-7B）专门做结构提取
```

| 优势 | 劣势 |
|------|------|
| ✅ 推理速度快、成本低 | ❌ 需要大量标注数据 |
| ✅ 不依赖大模型 API | ❌ 初期不现实 |

> **适合 Phase 3 长期优化**，初期不用。

### 4.3 推荐策略：分阶段演进

| 阶段 | 方案 | 数据量 |
|------|------|--------|
| **MVP (现在)** | B：LLM 提取 + 向量匹配 | 1-10 份 |
| **Phase 2** | B + C：加入聚类自动分组 | 50+ 份 |
| **Phase 3** | B + D：微调专用结构提取模型 | 100+ 份 |

> **永远不用 RL**——这个场景的反馈循环太慢、样本太少。

## 5. 多模型校验：方法论与实施方案

### 5.1 校验维度矩阵

投标文件的校验不是一个笼统的"看看对不对"，而是需要拆分成**具体可检查的维度**：

| 维度 | 检查内容 | 检查方法 | 由谁做 |
|------|---------|---------|--------|
| **结构完整性** | 招标要求的每个章节是否都有 | 招标 JSON vs 投标目录对比 | 代码 + LLM |
| **顺序正确性** | 章节顺序是否与招标要求一致 | 序号对比 | 代码 |
| **内容覆盖度** | 招标的每个评分项是否都有对应内容 | LLM 语义匹配 | LLM |
| **数据准确性** | 公司名、证照号、金额等是否准确 | RAG 来源交叉验证 | 代码 + LLM |
| **逻辑一致性** | 前后章节有无矛盾 | LLM 推理判断 | LLM |
| **合规性** | 是否有禁止性用语、虚假承诺 | 规则库 + LLM | 代码 + LLM |
| **缺项识别** | 哪些地方标记了[待补充] | 正则扫描 | 代码 |
| **格式规范** | 字体字号页边距是否达标 | python-docx 属性检查 | 代码 |

### 5.2 校验架构：三层校验法 ⭐

```
         ┌──────────────────────────────┐
 第1层    │     代码规则校验（秒级）      │  ← 确定性，零成本
         │  结构对比 / 缺项扫描 / 格式   │
         └──────────────┬───────────────┘
                        │ 通过后
         ┌──────────────▼───────────────┐
 第2层    │   主模型深度审阅（分钟级）    │  ← Qwen-Max
         │  内容覆盖度 / 逻辑一致性      │
         │  逐章节审查，输出问题清单      │
         └──────────────┬───────────────┘
                        │ 结果送入
         ┌──────────────▼───────────────┐
 第3层    │   交叉模型独立复核（分钟级）   │  ← DeepSeek + GLM-4
         │  对第2层发现的问题做二次确认    │
         │  + 补充第2层遗漏的问题         │
         └──────────────┬───────────────┘
                        │
         ┌──────────────▼───────────────┐
         │      合并校验报告              │
         │  ✅ 通过项 / ⚠️ 警告 / ❌ 错误 │
         │  每项附带：来源模型 + 置信度   │
         └──────────────────────────────┘
```

### 5.3 为什么不用"三个模型各自独立审"？

独立审的问题：
- 同一个问题被三个模型重复报告 → 需要去重
- 三个模型的审查标准不统一 → 结果矛盾难处理
- Token 成本 × 3（每个模型都要读全文）

**三层法的优势**：
1. 第 1 层用代码解决 60% 的确定性问题（零成本）
2. 第 2 层用最强模型做深度审查
3. 第 3 层只对第 2 层的结论做验证和补充（输入量小，成本低）

### 5.4 各层 Prompt 设计

#### 第 1 层：代码校验（无需 Prompt）

```python
def rule_based_check(tender_json, bid_document):
    report = []
    
    # 完整性：招标要求的每个章节是否存在
    for req_section in tender_json["sections"]:
        if req_section["title"] not in bid_document.sections:
            report.append({
                "level": "ERROR",
                "type": "MISSING_SECTION",
                "message": f"缺失章节: {req_section['title']}",
                "source": "rule_engine"
            })
    
    # 顺序性：章节顺序是否正确
    # 缺项：扫描 [待补充] 标记
    # 格式：检查字体/字号
    return report
```

#### 第 2 层：主模型深度审阅

```
你是一位资深投标文件审核专家。请严格审查以下投标文件章节。

【招标要求】
{tender_section_requirement}

【投标内容】
{bid_section_content}

请从以下维度逐一审查，输出 JSON 格式：
1. content_coverage: 是否完整回应了招标要求的每一项？遗漏了哪些？
2. logic_consistency: 内容是否有前后矛盾？
3. data_accuracy: 提到的数据（公司名、人名、金额、日期）是否看起来合理？
4. compliance: 是否有绝对化用语（如"全国第一"）、虚假承诺或违规内容？
5. quality_score: 1-10 分整体评分
6. suggestions: 改进建议（最多3条）

输出格式：
{"content_coverage": {"pass": true/false, "issues": [...]}, ...}
```

#### 第 3 层：交叉模型复核

```
你是投标文件的独立审核员。另一位审核员已对以下投标章节做了初步审查。
请你独立判断他的审查结论是否准确，并补充任何他可能遗漏的问题。

【招标要求摘要】
{tender_summary}

【投标内容摘要】
{bid_summary}

【初审结论】
{primary_review_result}

请输出：
1. 对初审每项结论的判断: AGREE / DISAGREE（附理由）
2. 初审遗漏的问题（如有）
3. 最终综合评级: PASS / WARNING / FAIL
```

## 7. RAG 知识库设计

### 7.1 数据分层

| 层级 | 存储方式 | 检索方式 | 数据举例 |
|------|---------|---------|---------|
| **L1 结构化** | PostgreSQL 表 | SQL 精确查询 | 律所名称、证照号、合伙人列表 |
| **L2 半结构化** | JSON + PostgreSQL | 字段匹配 | 招标模板库、资质证书清单 |
| **L3 非结构化** | pgvector 向量库 | 语义检索 | 历史标书方案、团队简历、业绩描述 |
| **L4 文件** | 文件系统/OSS | 引用链接 | 营业执照扫描件、审计报告 PDF |

### 7.2 语义检索准确性保障

- **Embedding 选型**: BGE-Large-zh（中文法律领域表现好）
- **相关性阈值**: similarity score < 0.7 的不引用，标记为"未找到匹配数据"
- **引用溯源**: 每段生成内容附带引用来源 ID，可追溯到原始文档
- **人工标注反馈**: 律师标记"引用不准确" → 调整 Embedding 或补充数据
